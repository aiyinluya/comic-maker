# 你的 Git 历史，是怎么"自己走出家门"的

> 码事漫谈 · AI 科普系列 · 配套漫画《加密包裹：从曝光到开源的三天》（第 20 话）
> 事实口径：全部来自公开报道与开发者逆向复盘，争议表述均标注「被曝 / 官方称」。

## 引入

2026 年 9 月 18 日，开发者圈炸了锅。起因特别日常：一位开发者觉得磁盘空间紧张，想看看 AI 编程工具 ZCode 的数据目录为什么吃了 700MB。结果在 `~/.zcode/v2/checkpoints` 底下，翻出了一个 313MB 的加密包。

顺藤摸瓜，摸出了一个大多数人都没想到的事实：**只要账号登录着，这个工具就会把你的整个工作区——代码、配置、甚至完整的 Git 提交历史——打包、加密、传到云上。** 默默地，不问你。

![第1格：小码举着手机惊呼](assets/20-zcode-incident/01.jpg)

这件事之后三天的发展堪称连续剧：当晚官方致歉，第三天开源。今天用大白话把整件事讲清楚——不是吃瓜，是这事儿跟每个写代码的人都有关。

## 它到底做了什么

### 一、包裹里装的是什么？

逆向分析的结论是：整个项目的快照。更扎心的是构成——**上传量里 86.6% 是 Git 历史**。

Git 历史是什么？是你这个项目从第一行代码到今天的全部脚印：每一版改动、每一条提交说明、改过的文件名、被删掉的敏感信息——如果你曾经把 API 密钥提交进仓库后来又删除，那份密钥仍然躺在历史里。代码可以重新写，历史没法伪造。所以说「Git 历史比代码更懂你」，不是修辞。

![第3格：Git 历史像一棵家谱树](assets/20-zcode-incident/03.jpg)

### 二、传到哪去了？

传到云端对象存储。而且是**加密后上传**——听起来是好事？坏就坏在那把钥匙：解密私钥只在服务端手里，你自己打不开自己代码的包裹。这相当于把保险箱寄存在别人家，锁是好的，但钥匙人家也有。

![第4格：传输线通向挂锁的云朵](assets/20-zcode-incident/04.jpg)

### 三、删了不就完了？

这才是最让人后背发凉的部分：没用。开发者第一次发现后直接删了 pending 队列里的归档，半小时后客户端重新捕获、重新打包出一份新的 313MB，重试计数器从 564 涨到 565。

**上传失败了 564 次，它还在锲而不舍地重试。** 一个 10GB 的商业项目，剔除依赖后 345MB 的核心资产，就这样被反复打包等待上传。这不是「功能」，这是一台永不停机的搬运机。

![第5格：撕碎又拼好的包裹和计数轮](assets/20-zcode-incident/05.jpg)

### 四、把隐私开关关上呢？

也关不掉。社区实测反馈，界面上的隐私开关关闭后，上传链路照样工作。开关在界面上，腿长在后台——这就是「默认开启」加上「关不彻底」的双重问题。

![第6格：开关拨向关闭，背后还在爬线](assets/20-zcode-incident/06.jpg)

## 官方怎么接的招

9 月 18 日晚，官方回应来了，口径是：问题出在「代码库索引（Repo Wiki）」功能，上线初期**默认开启**，生成 Wiki 页面时会触发仓库数据上传；云端生成后上传数据「立即销毁、不会保存」；已修复，向受影响用户致歉。

补救是三件套：**承诺开源客户端代码、邀请第三方审查并公布进展、全体用户补发一次周额度重置**（当天就发了）。

![第8格：礼盒、放大镜、硬币三件套](assets/20-zcode-incident/08.jpg)

平心而论，这个响应速度不算慢——当天曝光当天回应，三天后开源兑现。但社区也不是没有追问：被曝关闭开关仍上传怎么解释？有企业发函，要求书面回应、彻底删除数据及备份、提供数据处理清单。**风波没有因为道歉结束，只是换了赛道——从舆论场进入合规场。**

![第9格：盖着印章的信函](assets/20-zcode-incident/09.jpg)

## 9 月 21 日：代码真的挂上了 GitHub

第三天，承诺兑现：ZCode 开源，代码放在 GitHub 上接受社区监督，官方还专门感谢了发现问题的社区开发者。

![第10格：礼盒里升起分支树](assets/20-zcode-incident/10.jpg)

这事到这儿，算是一个不错的落点。用三个视角收个尾：

| 视角 | 这次事件教会我们什么 |
|---|---|
| 用户 | 「默认开启」的开关不等于你同意过；工具的每个数据出口都值得翻一翻 |
| 厂商 | 信任修复的速度本身就是产品力：认错快、兑现快，损失才止得住 |
| 行业 | AI 工具的数据边界需要行规：上传什么、存多久、钥匙在谁手里，默认答案应该是「本地」 |

![第11格：波普把分支树贴纸按在笔记本上](assets/20-zcode-incident/11.jpg)

漫画的最后一句是：**「认错的速度，也是信任的一部分。」**——工具会犯错，这在所难免；真正拉开差距的，是犯错之后那张时间表。

## 给你的三步自查清单

如果你装过 ZCode 或任何同类 AI 编程工具，花两分钟做这三件事：

1. **看一眼数据目录**：`~/.zcode/v2/checkpoints/`（或同类目录）有没有异常大的 `.enc` 文件——它的存在和大小直接告诉你被打包过多少；
2. **翻一遍设置页**：把所有带「上传 / 云端 / 索引 / 同步」字样的开关过一遍，确认每一项都是你主动选择的默认值；
3. **评估敏感仓库的暴露面**：轮换过期的密钥、清理 Git 历史里的旧凭证（`git filter-repo` 或 BFG），别把「曾经提交过」当成「没人看见过」。
